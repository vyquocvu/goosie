Goosie

An experimental web browser engine written from scratch in Go. It implements its own HTML/CSS pipeline, layout engine, display list, and rasterizer — no WKWebView, WebView2, CEF, or any other embedded browser. Fyne provides only the desktop window and input; everything that draws a page is Goosie's own code.

Go 1.25 Fyne v2.7 goja (ECMAScript) x/net/html oksvg / rasterx MCP go-sdk Playwright (E2E) Docusaurus

Goosie is a full engine, not a wrapper. A single navigation walks through a streaming HTML parser that builds an index-addressed DOM, a CSS cascade that produces computed styles, a layout engine that emits fragments, a retained display list, and a CPU rasterizer that writes pixels into a frame — then hands that frame to a Fyne window or writes it straight to a PNG. The whole thing is about 144k lines of Go across 484 files, of which roughly 290 are test files, committed over 571 commits.

Two things shape the design more than anything else. First, pure Go with no cgo in the rendering path: the JS runtime is goja rather than V8, the SVG stack is oksvg/rasterx rather than librsvg, and the rasterizer has a hand-written CPU backend. That is what makes a headless goosie-cli that renders a document to an image file, or a reproducible CGO_ENABLED=0 release binary, possible at all. Second, verification against a real browser: the project's own CI compares Goosie's rendered output against Chromium screenshots, so engine decisions are judged by pixel diff rather than by taste.

Scope is honest about being partial. HTML_CONFORMANCE.md tracks support for 110 of 132 MDN-documented HTML elements (83%), and website/docs/supported-web-platform.md lists the Web Platform surface that actually works. The current project phase in PROJECT.md — "Live URL Real-world Browsing & Subsystem Fixes" — covers DOM/JS completeness, CSS/renderer correctness, and the verification milestone, and all three are marked done.

Architecture

The engine is organised as a strict layering of internal/ packages, and the rule is enforced in prose and in review: a package may only import packages at its own layer or below, and no core engine package may import Fyne. The rule exists because the same engine has to serve three very different hosts — an interactive desktop window, a headless PNG writer, and a JSON-RPC automation server — and any Fyne type that leaked into layout or painting would make two of those three impossible. The authoritative map is website/docs/package-ownership.md.

The pipeline as the organising idea

Almost every layer boundary in the table above is a data-format boundary, and the canonical form is the display list. Parsing and styling produce a DOM plus computed styles; layout turns those into positioned fragments; the display list flattens fragments into backend-neutral paint commands; and only then does anything touch pixels. That sequencing is what makes the incremental behaviours possible at all — a DOM mutation from JavaScript can invalidate one subtree, re-layout it, and repaint only the dirty tiles, because each stage keeps its own retained structure instead of rebuilding the next one's.

The deliberate exception to "everything is core" is the automation boundary. internal/browsercontrol exposes a Service/Context interface that drives the engine without any window, and both internal/mcpserver (see MCP Automation) and cmd/perf-review consume it. Because that surface is UI-free, the performance profiler and the AI-agent server exercise exactly the code path the desktop browser does — which is what makes benchmark numbers meaningful. This boundary is recorded as an ADR: website/docs/adr/0004-*.md.

Reading order for the deep dives. website/docs/architecture-deep-dives.md indexes ten short design articles that map one-to-one onto the layers above: compact DOM store, streaming parser, style invalidation, incremental layout, retained display list, raster backend boundaries, compositor and tiles, memory budget, JS runtime isolation, and process isolation. Four ADRs in website/docs/adr/ explain the choices that were contested.

Startup and dependency wiring

cmd/browser/main.go is the composition root. It parses flags, opens the user profile, then constructs a session.Session, a net.Service with an HTTP cache, and a memory.Manager before creating the UI. Notably, the renderer is injected rather than imported-into-a-global: ui.NewBrowserWithDependencies receives a RendererFactory closure (renderer.NewRenderer(1000, 700)), so the shell never decides how an engine instance is created. The same factory trick is what lets the headless build swap in Fyne's test driver without touching engine code.

From there, a navigation is a coordinated, partly-overlapped sequence: stream-fetch the document, parse it incrementally while the byte stream is still arriving, let the resource coordinator discover and fetch CSS, scripts, fonts and images during that same download, wait for stylesheets to settle, then re-parse into the form the renderer consumes, paint, and run scripts in the correct classic/defer/async order. The details are in Rendering Pipeline and Networking & Resources.

Rendering Pipeline

This is the spine of the engine, and every subsystem described below exists to feed the next stage of it. One navigation runs fetch → streaming parse → resource coordination → style cascade → layout → display commands → raster. The stages are coupled only through data formats, which is what lets each one be replaced, cached, or run incrementally without touching the others.

fetch · stream parse → css cascade → layout → DisplayCommand · PaintChunk → raster · Fyne · PNG

Two details make the pipeline behave like a browser rather than a batch renderer. The first is that parsing and resource loading overlap: dom.Parser.ParseDocumentCtx emits discovered resources while the HTTP body is still streaming, so stylesheet and image fetches begin before the last byte arrives — and parser-blocking scripts deliberately stop that overlap, because the spec says so (see Networking & Resources). The second is that the expensive work never happens on the UI thread. internal/ui/renderer.go defines an HTMLRenderer interface and a frameSplitter that splits a frame into two phases: engine work off-thread, then PresentFrame on Fyne's goroutine. A slow layout can therefore delay a frame without freezing the address bar.

Lifecycle is observable rather than implicit. internal/engine/session/session.go drives a state machine through Navigate, Parsing, Interactive, and FirstPaint, recording each navigation with metrics.Recorder. Those stage timings are the same ones cmd/perf-review prints, so the numbers used for debugging and the numbers used for CI gates come from one instrumented source.

Where to look first. The end-to-end trace is easiest to read in cmd/browser/main.go's loadPageAsyncWithCoordinator, which calls each stage in order. The ten articles indexed by website/docs/architecture-deep-dives.md each cover one stage in more depth than this page can.

DOM & HTML Parsing

A browser's DOM is usually modelled as objects with parent and child pointers. Goosie deliberately does not, because that shape is expensive: an Element struct with attribute maps and slice-based children costs several allocations per node, and a real page is tens of thousands of nodes competing for the 100 MB DOM budget in Memory Model. The trade-off is recorded in website/docs/adr/0001.

The compact store

internal/dom/store.go keeps nodes in contiguous []nodeRecord slices addressed by a NodeID (uint32) handle, with first-child/next-sibling links instead of child slices, packed attribute storage, and a separate text arena. Traversal in internal/dom/store_traverse.go is written to allocate nothing. Handles are validated rather than trusted: a freed node's Kind is zeroed, so a stale NodeID is detectable instead of being a use-after-free equivalent. Tag and attribute names are interned through internal/dom/atom/, which is why the parser, the CSS matcher, and JS attribute lookups can compare small integers instead of strings.

The cost of that design is ergonomics — every API that looks "object-shaped" is a view over indices — and it is paid in two places: internal/dom itself, and the JS bridge, which cannot hand goja pointers into the store and instead uses its own identity scheme (DOM APIs in JS).

Streaming tree construction

Parsing has two entry points, and it matters which one you use. internal/dom/parser.go is a thin wrapper over golang.org/x/net/html that exists so an HTTP body can be parsed without buffering it into a string. The engine path is internal/dom/treebuilder.go, which drives html.Tokenizer by hand and feeds an internal treeBuilder. That control buys three things a plain html.Parse cannot do:

  • Early resource discovery. discoverResources emits Resource values tagged CSS, script, or image as tags are seen, so the coordinator can start fetches mid-document.
  • Script mode classification. Each <script> is classified classic, async, defer, or module at parse time — the ordering rules are enforced later by cmd/browser, which cannot make the right decision without this information.
  • Structure repair and diagnostics. ensureHtml/ensureHead/ensureBody, autoStructure, and autoCloseP synthesise the missing tags real pages omit, while detectUnsupportedFeatures records what the document asked for that the engine does not do — the feed for the conformance reports in Testing & Conformance.

The parsed result is a Document{Store, Root}. It is not what layout consumes: internal/engine/documentloader/dom_bridge.go converts it into the renderer's RenderNode tree. That bridge is the seam that keeps internal/dom free of layout concerns, and it is where the two representations are allowed to disagree.

Two document representations coexist. internal/dom holds the parse-level store; the renderer holds RenderNode; and goja holds a JS object graph. A DOM change is not automatically visible in all three — it must be propagated, which is exactly what the mutation channel in JavaScript Runtime is for.

CSS Engine

CSS is where a from-scratch engine either stays fast or becomes unusable on real sites, and Goosie's answer is to make matching cheap first and correctness second. The package is split from the renderer by an interface: internal/css matches against a css.Element abstraction, so the cascade knows nothing about layout boxes.

Parsing and the cascade keys

internal/css/parser.go is a hand-written single-pass tokenizer and parser producing StyleSheet, Rule, and AtRule values defined in stylesheet.go. It is bounded by a ParseConfig carrying MaxBytes, MaxImportDepth, and an Origin — the depth limit is what stops a pair of stylesheets that @import each other from hanging the parse, and the origin is a cascade input, not a label.

Each rule pre-computes its three cascade keys at parse time: Specificity [3]uint16, SourceOrder, and Origin (user-agent, user, or author). Pre-computation is the point — the cascade then reduces to comparing values that already exist rather than re-analysing selector text per element.

Rightmost-selector bucketing

The optimisation that keeps large pages responsive lives in internal/css/selector.go. Selectors are flattened into CompiledSelector slices, and rules are indexed into buckets keyed by their rightmost simple selector: idBucket, classBucket, tagBucket, attrBucket, and universalBucket on CompiledStyleSheet. Because a descendant selector like .card ul li > a can only ever match an a, matching starts from the element being styled and walks a candidate list built from that element's own id, classes, tag, and attributes — ancestor complexity does not multiply the candidate set. A bounded LRU MatchCache in match_cache.go, keyed by ElementKey, absorbs the repetition that survives bucketing.

Computed style and invalidation

The renderer-side consumer is StyleManager in internal/renderer/style.go, which caches preparedRules, resolves pseudo-classes and sibling combinators, applies media rules (including CSS Media Queries Level 4 range syntax, implemented in internal/renderer/media_query.go with the viewport pushed in via SetViewport), merges inline styles, and sorts the survivors by origin → specificity → source order. User-agent defaults come from internal/renderer/default_style.go and custom properties from internal/renderer/css_vars.go.

Computed values are split into InheritedStyle and NonInheritedStyle in internal/css/computed.go, with inherited groups fingerprinted so a subtree that shares an inherited state stores it once, and property names interned. When something changes, StyleInvalidator in internal/css/invalidation.go decides which subtrees must be recomputed rather than re-running the cascade over the document — the input to the reflow roots in Layout.

Conformance detail worth knowing. internal/css/fuzz_test.go and adversarial_cascade_test.go exist because CSS parsing is the widest attack surface in the engine: it is unvalidated remote text. Parser limits above are security-relevant, not just politeness.

Layout

internal/renderer/layout.go exposes the one function everything else waits on: LayoutEngine.ComputeLayout(*RenderNode) *LayoutBox. It builds the tree defined in layout_tree.go, where each LayoutBox carries a Rect, a DisplayType (block, inline, none, flex, grid, inline-block), and the margin/padding/border triple — the box model, concretely. Layout engines for the special display types are held by LayoutEngine and pooled for reuse across builds.

Block-in-inline: why anonymous boxes appeared

The most recent substantive layout work (commit 1d494db) was block-in-inline handling, and it is a good illustration of how spec conformance shows up as data structure. CSS does not allow a block-level box to sit inside an inline box, but authors write <span>text <div>block</div> more text</span> constantly. The correct rendering splits the inline into pieces: consecutive inline siblings are grouped into anonymous block boxes that interleave with the block child, so the inline content before and after the <div> become separate blocks. The split happens in layout.go (around the inline-grouping code) and inline_layout.go, and is pinned by internal/renderer/block_in_inline_test.go. Without it, real pages place content at the wrong vertical offset in a way that is very hard to notice except in a Chromium diff.

Incremental reflow and dirty regions

Full-tree layout is the simple model, and it is what ComputeLayout still does per build — but a page-wide relayout on every hover would miss the interactivity budget in perf-review's gates. internal/renderer/incremental_layout.go adds a ReflowTracker with MarkDirty and FindReflowRoot, so a mutation reflows the smallest ancestor whose geometry can absorb the change, plus an intrinsic-size cache so containers that only depend on min/max content do not re-ask their children. Dirty rectangles from that tracking feed dirty_region.go, which is what lets the painter in the next section rasterize a subregion instead of the viewport.

The fragment store (fragment_store.go) is the other half of the same idea: layout output is retained so that painting and hit-testing can work against stable records rather than re-walking a tree, matching the retained-display-list decision in website/docs/adr/0002.

Paint, Raster & Compositing

There are two paint contracts in the renderer, and the reason for both is that Goosie has two very different consumers of the same layout result. Understanding which one you are looking at prevents a lot of confusion while reading this package.

ContractFileCommandsConsumed by
Legacy canvas pathdisplay_list.go → canvas.goPaintCommand: Text, Rect, Image, Link, Border, Button, Input, PushClip/PopClipCanvasRenderer builds Fyne canvas objects — the interactive UI, where widgets need to exist as Fyne nodes.
Backend-neutral path (M5.1)displaycmd.go → paint_chunk.go → incremental_painter.goDisplayCommand: Rect, Border, Text, Image, Push/PopClip, Transform, Opacity, StackingContextRasterized into a backbuffer image by IncrementalPainter.PaintDirty/PaintFull.

The newer contract is the architectural one: DisplayCommand is the stable layout → paint boundary (ADR website/docs/adr/0002), grouped into PaintChunks so that a chunk is the unit of invalidation. Raster backends sit behind it in internal/renderer/frame/raster/: a pure-Go CPU backend (cpu_backend.go) and a macOS Core Graphics backend (cg_backend_darwin.go, with its own font registry) selected by build tags. The abstraction is the subject of website/docs/adr/0003 and of website/docs/architecture-deep-dives.md's raster-boundary article — the point being that pixel output must be reachable with no GPU, so cmd/headless and CI goldens can run anywhere.

Compositing lives in internal/renderer/frame/compositor/ as a 256×256 tile compositor with frame budgets and a viewport policy, plus glyph and image caches under frame/cache. Tiles are the unit that survives scrolling: a scroll can reuse most of what is already rasterized, which is why scrollcoalescer.go gates scroll presents to frames and coalesces multiple wheel events into one repaint. That pair — tile reuse plus coalescing — is what keeps scroll p50 under the 5 ms budget.

Images and SVG

Raster image decoding, an LRU cache, and network loading sit in internal/image: loader.go handles png/jpeg/gif/webp, data: base64 URIs, and HTTP with 429 backoff, modelling async load state (LoadState plus OnLoadCallback) so an unloaded image reserves its box instead of collapsing it. svg.go detects SVG content with IsSVGContent and rasterizes through oksvg + rasterx — again pure Go, no external SVG library. Headless raster output for snapshot and golden tests is produced by internal/renderer/headless.go.

JavaScript Runtime

Goosie runs scripts with github.com/dop251/goja, a pure-Go ECMAScript engine. That choice is not incidental: goja needs no cgo, so JS runs in the same process as a CPU-rasterized frame and inside the same static binary as everything else (see Architecture). The price is that Goosie owns everything goja does not provide — the DOM, the window object, events, timers, and the concurrency model around a VM that is explicitly not safe for concurrent use.

internal/js/runtime.go is the host: 3,792 lines of the package's ~13k, and by far the largest single file in the repository. NewRuntime() creates the goja VM, injects polyfillsJS from polyfills.go (a hand-written queueMicrotask, Promise, and timer helpers), then installs the console, window, and document APIs plus a frame scheduler.

One owner goroutine, everything else submits

A goja VM cannot be driven from several goroutines at once, but a browser has several things that want to: a timer firing, a fetch completing, a user clicking, a script calling document.querySelector. internal/js/session.go resolves this with an ownership model (milestone M8.1): exactly one goroutine owns the VM, and everyone else submits Tasks through Submit, SubmitAndWait, or Eval into a bounded 256-entry ring queue. The runtime's enqueueTask hook is how asynchronous completions — timer callbacks, network responses — get back onto the owner goroutine instead of executing wherever they happened to finish.

Direct execution goes through RunScript, which serialises VM access with a mutex, scans sources for constructs the engine cannot honour such as dynamic import() (runtime_import_scan.go), can interrupt a runaway script using goja's Interrupt via SetMaxTaskDuration, counts long tasks against the W3C 50 ms definition, and flushes the polyfill microtask queue after each run.

There are two timer systems. setupTimerAPIs in runtime.go implements setTimeout/setInterval on Go time.AfterFunc and tickers, while a second, independent scheduler exists in eventloop.go whose RunOnce drains one macrotask, then microtasks, then due timers, then pending DOM mutations. When changing timer or queue behaviour, check both — a task queued into the wrong scheduler will run at the wrong time rather than failing.

requestAnimationFrame is real, and it is a separate file for a good reason. framescheduler.go accumulates RAF callbacks until the GUI calls Tick() after presenting a frame. Previously RAF was a synchronous microtask-recursion polyfill, which let a page that re-registered inside its own callback starve the host and freeze the browser; deferring to the frame boundary is what ties animation to actual presentation.

Capability gating and script limits

Because scripts are untrusted input, internal/js/policy.go adds a ScriptEnforcer with execution ceilings (MaxSteps, timer and queue caps), a DocumentMode covering no-script and inline-only pages, and per-origin capability gates for network, storage, navigation, clipboard, notifications, and geolocation. fetch is available only when gated on, via HTTPFetcher; window.open honours popup blocking.

Unsupported platform features are reported rather than silently missing. runtime_pwa_workers.go provides reporting stubs for WebSocket, Worker, and ServiceWorker that emit dom.UnsupportedFeatureKind, the same mechanism the parser's detectUnsupportedFeatures uses (streaming tree construction), so the fallback layer and the conformance audit can both see what a page asked for.

DOM APIs in JS

This is the most unusual part of the codebase, and it will confuse anyone expecting Go structs projected into JS. The DOM classes are not Go types — they are JavaScript, written as a large embedded script. setupDocumentAPI in runtime.go installs a ~1,260-line jsDOMScript string that defines Attr, NamedNodeMap, Event, CustomEvent, EventTarget, Node, TextNode, Element, and Document on globalThis. Writing the façade in JS means the semantics are exactly the ones the spec describes — subclassable, iterable, extensible — without a proxying layer in Go getting in the way.

The consequences of that choice are visible in the API surface: NamedNodeMap is Proxy-backed so it supports index access, named access, and Symbol.iterator; Element exposes classList, dataset, closest, and a style Proxy with setProperty/getPropertyValue; innerHTML assignment round-trips into Go for re-parsing. Commit 90d93a2 replaced the earlier ad-hoc listener maps with this full EventTarget and NamedNodeMap implementation and expanded Location, adding roughly a thousand lines of tests with it (dom_api_test.go, adversarial_challenge_test.go).

The bridge: identity attributes and serialization

The JS object graph and the Go DOM store are separate, and the bridge between them is an element identity attribute named __goosie_id:

populateDocument → JS calls __querySelectorGo → serializeJSDOMToCache → Go dom.Parser.QuerySelector → resolve to JS objects

populateDocument walks the parsed *html.Node tree to hydrate document, head, and body. A selector query from JS calls __querySelectorGo/__querySelectorAllGo, which serialize the live JS DOM back to HTML (serializeJSDOMToCache), re-parse it with Go's dom.Parser.QuerySelector(All), and return __goosie_id values that __findElementByGoosieId resolves to JS objects. Mutations travel the other way: window.__onDOMChanged(kind, …) reaches __onDOMChangedGo, which produces typed DOMMutation structs in mutation.go and delivers them through SetDOMMutationBatchCallback to the renderer, coalesced on a 16 ms MutationCoalescer so a loop of appendChild calls produces one relayout. Structural changes still fall back to a legacy full-serialization callback.

Read this before optimising a selector path. Because every query round-trips through HTML serialization and a Go re-parse, DOM results in JS are snapshots rather than live views on the layout tree. The design chooses correctness-per-query over speed, and it is the known hot spot for script-heavy pages.

Events, and what is not wired

EventTarget.dispatchEvent is pure JS: bubbling up parentNode, once and handleEvent support, stopPropagation and preventDefault. Lifecycle events originate in Go — fireDOMContentLoaded in cmd/browser/main.go dispatches DOMContentLoaded on document after classic and deferred scripts complete, and the documentloader coordinator emits EventDOMContentLoaded/EventLoad. The automation layer synthesizes input by evaluating JS: internal/browsercontrol/engine_context.go calls el.click(), dispatches input/change events with bubbles: true, and fires KeyboardEvent('keydown').

Honest gaps, all of which are load-bearing for anyone extending this layer: dispatch has no capture phase; real mouse input from the Fyne shell is not connected to DOM pointer events; getComputedStyle returns inline styles only; getBoundingClientRect is stubbed, so layout is not observable from JS; MutationObserver, IntersectionObserver, and ResizeObserver are stubs. A vestigial Go-side eventListeners map is populated by addEventMethods but never dispatched, and website/docs/contributing-dom-apis.md still references removed dom_handle.go/NodeHandle code — trust the source over that page.

Window-level APIs are implemented where they are cheap and safe: setupLocationAPI covers href, protocol, host and friends plus reload, setURL, query-parameter helpers and an OnNavigate hook; setupHistoryAPI and origin-scoped localStorage/sessionStorage sit behind a pluggable LocalStorageAdapter, alongside crypto and navigator.

Networking & Resources

A browser engine's network layer is not an HTTP client; it is an HTTP client plus a resource policy, a cache, and a scheduler that has to cooperate with a parser that is still running. Goosie splits those responsibilities between internal/net (mechanism) and internal/engine/documentloader and internal/engine/navigation (policy and ordering).

internal/net/service.go owns the single http.Client — cookie jar, httptrace timing, TLS — and applies the ceilings that keep a hostile server from ending the process: a 100 MB MaxBodySize and a decompression-ratio guard against gzip bombs. Fetcher (fetcher.go) wraps it while preserving ResponseMeta, including the CSP header parsed in csp.go, because security policy is decided by the coordinator but carried by the response. A bounded HTTP cache (cache.go), MIME sniffing, downloads, and a SecuritySummary in security.go complete the layer.

The coordinator

internal/engine/documentloader/coordinator.go is where the pipeline's overlap is actually implemented. Resources discovered by the streaming parser arrive at HandleResource or EnqueueSecondary, get CSP-checked, and are prioritized through priorityFor into a navigation.Priority. Two behaviours matter most:

  • Parser-blocking scripts block. isBlockingKind identifies the classic, non-async scripts that must pause parsing, which is the difference between a page that works and one whose scripts see a half-built DOM.
  • Load events wait. HandleDocumentEnd drains pending stylesheet loads before firing lifecycle events, so first paint and load observe a styled document. Font and image discovery during the same stream is what makes the first frame arrive earlier.

URL policy sits in internal/engine/navigation: a scheduler with rate limits, origin policy, and — for local files — CheckFileAccess in file_access.go, which allows file:// subresources only from a file:// page or the initial navigation. That single predicate is the barrier between "open a saved page and its images work" and "a random website can read your disk". data: URLs never hit the network; they are decoded in the image loader (Images and SVG).

Session history is still intentionally simple: a URL stack with GoBack/GoForward/CanGoBack in internal/ui/state.go, rather than a per-document history item model with restore states.

Memory Model

Every stage of the pipeline retains something — DOM nodes, computed styles, layout boxes, display commands, tiles, glyphs, decoded images, scripts — and a renderer that lets each grow freely will exhaust memory on a long page before the user scrolls it. Goosie's answer is a single accounting authority rather than per-component limits scattered through the code: internal/memory/manager.go.

The manager tracks eleven components (dom, style, layout, display-list, tile, image, glyph, script, network-cache, page-cache, layout-intrinsic-size). Components call UpdateUsage with their current byte total; checkLimitsAndEvict then enforces both the per-component limit and the global one by invoking the Evictor callbacks each subsystem registered with RegisterEvictor, walking them in a fixed order until usage falls back under budget.

ComponentBudgetWhy this size
dom100 MBLargest single allowance — and the reason the compact store in DOM & HTML Parsing exists at all.
style, layout, tile, network-cache50 MB eachStyle, layout and the compositor tiles are the retained structures that grow with document size.
image30 MBDecoded bitmaps are the fastest way to blow a budget, hence the LRU in internal/image/cache.go.
display-list, script, page-cache20 MB eachRetained commands and back/forward cache entries.
glyph10 MBSmallest — a glyph is small and recomputation is cheap.

Those caps are wired in cmd/browser/main.go against a GlobalLimit of 512 MB. Note that the per-component numbers already sum to the global limit, so the global ceiling is the real one and the per-component budgets are fairness, not headroom.

The eviction order is the interesting design decision: network-cache and page-cache go first, then style, glyph, image, tile, display-list, layout-intrinsic-size, and layout, with dom and script last. That ordering is ranked by recomputation cost: throwing away an HTTP cache entry costs a request, dropping a style or glyph cache entry costs CPU, but discarding layout means re-running the engine, and discarding the DOM or script state is user-visible breakage. So pressure is absorbed by the cheapest-to-regain things first.

Tuning is measured, not guessed. internal/memory/tuning.go adds EvaluateConfig and AutoTune, which run a supplied workload function against candidate configurations and report statistics, plus WriteHeapProfile and StartCPUProfile helpers. internal/browsercontrol/fake.go and the manager's observable eviction test make the cascade testable without a real page.

Browser Shell & UI

internal/ui is the only package allowed to know Fyne exists, and it is thinner than its 15.9k lines suggest because much of that is DevTools panels and their tests. internal/ui/browser.go (2,285 lines) is the shell: a Fyne app using container.DocTabs for tab management (Tab/AsTabItem, CreateTab, OnClosed), with the address bar in address.go, navigation state and the history stack in state.go, keyboard shortcuts, console output, an inspect panel, and screenshot capture each in their own file.

The rendering boundary is the part that matters for engine work: renderer.go declares an HTMLRenderer interface and the frameSplitter two-phase presenter described in Rendering Pipeline — engine build off-thread, PresentFrame on the UI thread. The shell receives a renderer from a factory injected at construction, so internal/ui never decides how an engine instance is created, which is what lets the headless build replace it.

DevTools lives in internal/ui/devtools/, with a dock.go and panels for network, memory, sources, performance, security, storage, accessibility, display list, tile cache, and script queue. Those last three are engine-specific rather than web-standard: being able to look at the retained DisplayCommand list, the compositor's tile states, and the JS task queue is what makes the incremental behaviours debuggable at all. Panel screenshots used in documentation are in screenshots/, and docs/screenshots/ holds rendered fixtures (CSS demo, forms, grid, tables, long page) used by the README.

Testing & Conformance

Goosie's testing thesis is that an engine is only correct relative to a real browser, so the suite is built around comparison rather than assertion. Concretely: 291 test files contain roughly 3,000 test and benchmark functions (384 of them benchmarks), and the top-level design in TEST_INFRA.md is a four-tier methodology — category partitioning, boundary values, pairwise combinations, and real-world workload — evaluated against ten named live websites.

Goosie vs Chromium

The keystone is CompareGoosieVsBrowser in test/e2e/utils.go. For a fixture it renders the HTML with Goosie's own renderer through testutil.RenderToImage, loads the same document as a file:// URL in Playwright-driven Chromium, injects font-normalizing CSS (an -apple-system stack and line-height: 1.2 so text differences reflect layout bugs rather than font choice), and pixel-diffs the two PNGs with compareImages — writing a red-highlighted diff image whenever a fixture exceeds its threshold. Sibling helpers cover the other axes: CompareScreenshot for baseline regression, ValidateDOMSnapshot for computed-style JSON, and imagesSettled to wait on <img> loads. Playwright itself starts in test/e2e/main_test.go's TestMain, with BROWSER=chromium|firefox|webkit to change the reference engine.

TestComprehensiveSuite in test/e2e/suite_test.go globs every testdata/test_*.html fixture — 130 generated files across 15 categories (typography, layout, flexbox, grid, forms, media, tables, css_advanced, edge_cases, and six smaller groups), rebuilt by make generate-test-data — and runs three subtests per fixture: Visual, DOM, and GoosieVsBrowser. The default diff threshold is 0.1%, and categories carry per-float overrides because some things will never match a different font stack: 0.05 for colors and backgrounds, 0.08 for flexbox, 0.15 for typography and border radius, 0.30–0.45 for media, edge cases and tables, up to 0.35 for general layout, 0.55 for advanced CSS, and 0.80–0.85 for grid and forms. Treating those as reviewed tolerances rather than failures is what keeps the suite usable as a gate.

Artifacts land in test/e2e/testdata/: baselines and snapshots in {baselines,snapshots}, and evidence in results/{goosie,browser,diffs_compare,actual,diffs}. Targeted behaviour has focused fixtures too — DOM mutation, HTML5 semantic layout, linked SVG images, and scroll coalescing, each with its own tight threshold (0.01 for the SVG case). Offline goldens sit closer to the engine in internal/renderer/layoutgolden/ (with serialize.go and an adversarial_determinism_test.go) and internal/renderer/frame/golden/.

Snapshots are evidence, not a checkbox. UPDATE_SNAPSHOTS=true (or make update-snapshots) re-records baselines, and the repository's own rules in AGENTS.md forbid using it to hide a regression: a baseline change must come from an intentional expected-output change, with the diff artifacts reviewed. For any user-visible change, a Goosie screenshot alone is not verification — the comparison against Chromium is mandatory before the work counts as done.

Live-URL tiers

Because synthetic fixtures cannot catch the ways real websites break an engine, test/e2e/live_urls_test.go runs TestLiveURLs against ten sites in four tiers, documented as status in TEST_READY.md. Tier 1 is five checks per site — navigation, title, DOM snapshot, a 1280×800 PNG raster, and a JavaScript-safety probe; tier 2 adds boundary cases, tier 3 cross-feature interaction, and tier 4 workload sweeps. These need network access and are excluded from the default run: they are compiled only with -tags="e2e online", i.e. make e2e-online.

Element conformance tracking

HTML_CONFORMANCE.md is generated, not maintained by hand: make html-audit runs cmd/html-audit over internal/conformance/registry.go and audit.go, using MDN's element reference as the source of truth, and currently scores 110 of 132 standard elements supported (83%) with 22 partial and none missing. The workflow it documents is deliberately narrow — pick one element, reproduce with go test ./internal/conformance -run TestElementAudit -v, fix the user-agent defaults in internal/renderer/default_style.go, then verify with TestHTMLConformance in test/e2e/html_conformance_test.go. That last test compares per-element computed style and geometry against Chromium (display, font properties, text alignment and decoration, white-space, margins, box size), scores matched/applicable, and is guarded by a ratcheted baseline in test/e2e/baselines/html_conformance_baseline.json — re-recorded only with HTML_CONFORMANCE_UPDATE=true when the score improves, so conformance can move in one direction.

cmd/browser's headless mode is build-tag gated, which surprises people the first time. Passing -headless to a normal build is rejected by cmd/browser/headless_app_disabled.go; the real implementation in headless_app.go is compiled only with -tags headless (make build-headless), and it substitutes Fyne's test.NewApp() driver for a GL window. The reason is that screenshot output must be deterministic — a GPU-backed window on an unknown driver is not.

Each binary parses flags with the standard library, and the option-parsing code is kept in its own function so behaviour can be tested without executing the program. cmd/perf-review is the clearest example: parseOptions() builds a private flag.NewFlagSet and is covered directly by cmd/perf-review/main_test.go, following the refactor(perf-review): isolate CLI option parsing change.

What perf-review actually checks

cmd/perf-review is not just a timer — it encodes the project's interactivity budget. It reports p50/p95/p99 for each pipeline stage and applies "freeze health" thresholds: scroll p50 must stay under 5 ms and mutation p95 under 50 ms. Those numbers reappear as regression gates in CI (CI/CD & Releases), so a layout change that makes scrolling stutter fails a check rather than being noticed by hand.

MCP Automation

Goosie speaks Model Context Protocol, which means an AI agent can drive the engine the same way a user does — create a context, navigate, take a snapshot, click, type — over stdio or HTTP. This uses the official github.com/modelcontextprotocol/go-sdk and lives entirely in internal/mcpserver: server.go builds the MCP server, registers ten tools and one resource via AddTool, and wires either a stdio or a Streamable HTTP transport. The tool names are declared in tools.go:

ToolWhat it does
browser_context_create / list / closeLifecycle of isolated browsing contexts, each with its own session and tab set.
browser_navigateLoad a URL into a context's active tab.
browser_snapshotStructured accessibility/DOM snapshot for programmatic reading.
browser_screenshotRendered frame as an image.
browser_page_infoTitle, URL, and document metadata.
browser_querySelect nodes from the document.
browser_click / browser_typeDispatch synthetic input into the engine.

The important structural decision is that the MCP server never touches internal/ui. It talks to internal/browsercontrol.EngineService, the same UI-free service the GUI-independent tests use, so there is no hidden dependency on a window existing. That is also why cmd/mcp-server can run in CI or inside another application. The boundary is documented in website/docs/mcp-architecture.md, with the wire contract in mcp-protocol-contracts.md and the threat model in mcp-security.md.

Serving it is not unauthenticated by default. cmd/mcp-server applies rate limiting and per-context quotas (internal/mcpserver/quota.go), and --auth --auth-token accepts either a literal token or an env:VAR_NAME indirection for HTTP binds. Prefer stdio, or loopback-only bindings, unless you deliberately pass a token via env.

Profile & Config

There is no config file to hand-edit and no environment-variable configuration layer at runtime. Persistent state is a user profile, owned by internal/profile, and it is treated as data the browser mutates rather than as program configuration.

profile.Open() resolves a directory under os.UserConfigDir()/goosie (falling back to ./.goosie when that is unavailable) and loads JSON stores for bookmarks.json, history.json, settings.json, session.json, and storage.json. Writes go through a 200 ms coalescing background writer that replaces files via atomic temp-file renames, with an in-memory snapshot serving reads — so rapid navigation updates do not hammer the disk and a crash mid-write cannot truncate the profile. Schema changes are handled by a versioned migration path recorded in schema.json; the v0 → v1 migration, for example, converts legacy string-array bookmarks into the current structured form.

Runtime behaviour that users do change lives in settings.json via internal/profile/settings.go: homepage, default_search_engine, enable_javascript, enable_images, and DevTools state, with Export/Import for portable JSON. Passing -private keeps all of it in memory, which is why private mode is threaded through the profile API rather than implemented as a "delete on exit" sweep.

Two other configuration facts worth knowing up front. The default user agent is a Chrome/120 string set in internal/net/service.go, overridable through ServiceOptions.UserAgent; the image loader deliberately identifies itself as goosie/1.0 (...; like Gecko) instead (internal/image/loader.go), because some hosts reject unknown UAs for images but not for documents. Memory budgets are not configurable either — they are hardcoded in cmd/browser/main.go as a 512 MB global with per-component caps, explained in Memory Model.

Environment variables are test-only. UPDATE_SNAPSHOTS, GOOSIE_SCREENSHOT_DIR, HTML_AUDIT_WRITE, and HEADLESS=true influence generated artifacts and suites, not engine behaviour. See Testing & Conformance before reaching for them — UPDATE_SNAPSHOTS in particular is treated as a reviewed change, not a fix.
