# What this says and what it does not. The document is 20,000 device px tall, which is 79
# tile rows by 12 columns; the cache settled at 228 of its 256 buffers and did not ask
# for more, so the plateau is reached by drawing the page rather than by a driver
# scripting a sweep. It is not a binding-cap demonstration - see section 2 on that.
#
# The frame numbers describe the last 120 presents, not the 3581 the session made: an
# interactive run's recorder ring is 120 deep, and a report cannot describe more than it
# kept. fps=4.0 is 120/29.86 and is an artifact of that cap, not a rate. The mean of
# 0.266 ms is a tail of unchanged frames, which is the cheapest 120 frames there are.
# Nothing in CI reads an interactive run's numbers.
#
# What is worth acting on later, and is not an M1 criterion: presents=3581 with
# plans_published=1 and zero_work_frames=120. An idle window re-presents its unchanged
# frame on every vsync it services, because surface.Loop.draw presents whenever a plan
# exists and a plan always exists after the first publish. About half of those presents
# are refused for want of a free surface (dropped=1797), which costs roughly a present's
# worth of UI work and a slot in the three-buffer ring each time. Skipping a present with
# an empty damage list is the obvious fix; it belongs with the throttle described in
# convention 2, not as a late M1 change.

# ---------------------------------------------------------------------------
# Measurement conventions - the things that make two numbers here disagree
# ---------------------------------------------------------------------------
#
# 1. mean_ms is not the same quantity on the two backends, and only the native one is
#    gated. The shim timestamps a vsync when its pump hands the event to Go, so the
#    native mean is the UI thread's own work: plan, submit, compose, present. The
#    headless window timestamps it when its clock fires, so its mean also carries how
#    long the tick waited behind the frame before it - which is why the same pipeline
#    reports 1.498 ms through AppKit and 6.981 ms through a timer. Criterion 7 says "UI
#    thread work", so the pump-read convention is the one that matches the criterion.
#
#    This is also why the run line's backend matters: a headless artifact and a native
#    artifact have the same shape and different units. See "Corrections made while
#    recording this baseline" below, which is about exactly that mix-up.
#
# 2. CVDisplayLink ticks at ~119 Hz on this ProMotion panel while Core Animation commits
#    this layer at ~59 Hz, so about half of all presents find all three surfaces still
#    owed to the display and return GOOSIE_DROPPED (queued=296 dropped=304 committed=295
#    above). The frames that do commit are complete and correct - a dropped present marks
#    the surface so the next one uploads the whole surface rather than its own damage
#    rects (see GoosiePresent's need_full) - and the effective displayed rate is the
#    commit rate. The dropped work costs 1.5 ms a frame, which is why it has not yet been
#    worth throttling vsync delivery on buffer availability; that change also risks
#    stalling the loop on a release callback that never arrives, so it is not free.
#
# 3. fps in a run line counts the ticks the display produced, not the commits the display
#    showed, and for an interactive run it is capped by the recorder ring (section 4). Use
#    the present line for the second.
#
# 4. -bench (headless, 1 microsecond period) reports a mean_ms in the hundreds - 226.998
#    for a 2000-frame run, fps=554.4, dropped_vsyncs=374230 - and both are correct: the
#    clock outruns the loop by orders of magnitude, so every mean is mostly queue depth.
#    Only the fps line in that mode means anything, and nothing gates it.
#
# 5. writes and bytes are device pixels: a 2880x1800 viewport at DPR 2 is what the
#    1.498 ms bought. Halving the viewport is not comparable to these numbers.
#
# 6. The window that was measured is not the window that was asked for. A 1440x900pt
#    request reported window=2880x1654 device px: AppKit constrained the height to the
#    display's visibleFrame, the resize event propagated, and the frame path re-sized its
#    composer, so the timings belong to the window that was on screen. The headless runs
#    report window=2880x1800 - nothing constrains a surface with no title bar - which is
#    one more reason the two backends' means are not one quantity.
#
#    The two size sources do not agree to the pixel, and this is an open item rather than
#    a settled fact. A 1200x800 request reported window=2400x1600 (2x, unconstrained)
#    while CoreGraphics listed that window's frame as 1176x816+168+48 points. CGWindowList
#    bounds include the title bar and the shim reports the content layer, so the
#    discrepancy is expected in height and not in width. Nothing in M1's criteria reads a
#    width that closely; M2's pixel comparisons against Chromium will have to, so the
#    shim's size source should be pinned down before then.

# ---------------------------------------------------------------------------
# Corrections made while recording this baseline
# ---------------------------------------------------------------------------
#
# cmd/goosie's run line used to print the backend the machine could open rather than the
# one the run drew through: platform.Available() answers "does this Mac have a window
# server" before anything is opened, so a `-backend headless` gate run on this machine
# reported backend=darwin interactive=true while no window existed.
#
# That is not a cosmetic label. The nightly job's "Require that the run was paced by a
# display" step greps that line, so before the fix the step could not fail: a macOS runner
# with no window session would fall back to headless, print darwin anyway, and have its
# 16 ms budget enforced against timings measured on a 16 ms timer. Both were fixed - the
# report now asks the window (platform.WindowName, satisfied by a Name() on each
# backend), and the workflow names -backend native so a fallback is an error exit before
# it is a mislabelled artifact. TestWindowNameReportsTheWindowNotTheMachine in
# v2/test/platform is the counter-only guard: it asserts a headless window does not report
# the machine's native backend where one exists.
#
# Every number in sections 2 and 4 was produced after that change, and each run line here
# says which window it actually used.
